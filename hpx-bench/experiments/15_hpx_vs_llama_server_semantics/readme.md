# Experiment 15 — hpx-server vs llama-server semantic alignment

Phase 0: **post-N5a/N5b semantic-alignment revalidation**, not a
performance benchmark.

## Purpose

Re-prove what can and cannot be compared fairly between
`llama-hpx-server` and upstream `llama-server` on the same model
(TinyLlama 1.1B Q4_K_M), the same prompts, the same greedy sampler
pinning, and the same EOG-stop handling that the M8 pair-run harness
already established. The hpx-server binary used here includes both
recent lifecycle fixes:

- **N5b**: shutdown liveness for queued-but-unadmittable requests.
- **N5a**: `cancel_freed` → natural completion → later admission slot
  recovery in `finalize_and_fulfill`.

Phase 0 does not exercise cancellation or shutdown drain, so the
canonical greedy anchors are expected to be unchanged. The point of
Phase 0 is to record that fact explicitly before any Phase 1 timing
comparison is contemplated.

## Reuse of Exp12 (M8) harness

This experiment writes **no new driver and no new adapters**. It
reuses the harness and adapters in
`hpx-bench/experiments/12_hpx_vs_llama_server_pair/` unchanged:

- `bench.py` — Python 3 stdlib only, single-config-JSON driver. Boots
  one server at a time, never both concurrently. Records raw values
  only.
- `adapters/hpx_server.py` — hpx-server `/completion` non-streaming
  and SSE streaming.
- `adapters/llama_server.py` — llama-server `/completion` with the
  M8d-fix pinned greedy sampler set (`temperature=0`, `top_k=1`,
  `samplers=["top_k","temperature"]`, `seed=0`, etc.).
- `known_mismatches.txt` (generated by `bench.py` into each results
  dir) — the canonical list of acknowledged hpx vs llama-server
  semantic differences. Inherited verbatim.

This directory only contains:

- `config.phase0.nonstreaming.json`
- `config.phase0.streaming.json`
- `config.phase1.nonstreaming.json`
- `config.phase1.streaming.json`
- `facts.md` (design-time facts and anchors)
- `results.md` (Phase 0 and Phase 1 run records)
- `.gitignore` (`results/` subtree)

## How to run

From the Exp12 directory, pointing `bench.py` at the Phase 0 configs
and re-rooting results under Exp15:

```text
cd hpx-bench/experiments/12_hpx_vs_llama_server_pair

python3 bench.py \
  --config       ../15_hpx_vs_llama_server_semantics/config.phase0.nonstreaming.json \
  --results-root ../15_hpx_vs_llama_server_semantics/results

python3 bench.py \
  --config       ../15_hpx_vs_llama_server_semantics/config.phase0.streaming.json \
  --results-root ../15_hpx_vs_llama_server_semantics/results
```

Capture driver `stdout`/`stderr` under
`local/runs/exp15/phase0-{nonstreaming,streaming}/` (gitignored).
Each run produces a `results/<run-id>-pair/` subtree with
`config.json`, `client_results.jsonl`, `summary.csv`, per-server
`stdout`/`stderr`/`args`, `known_mismatches.txt`, `match_conditions.json`,
and `run_notes.txt`. Both servers are launched strictly sequentially.

## Canonical hpx-server anchors

Phase 0 expects these to hold across all iterations of the
corresponding shapes:

```text
hpx p0_b8:  hash = 0x0619d4d1900c2365, n_decoded = 8
hpx p0_b32: hash = 0x6794e47fe0f84af1, n_decoded = 32
hpx p1_b8:  n_decoded = 0, hash = 0x0000000000000000, empty text
            (documented EOG-stop behavior on TinyLlama;
            engine.cpp EOG branch finalizes as completed without
            appending the EOG token)
```

Anchor drift is a real correctness signal, not a harness problem.
The right response to drift is to stop and triage, not to retune the
harness.

## Phase 1 — single-client timing comparison

Phase 1 reuses the same Exp12 driver and adapters at a larger sample
size to record single-client client-observed latency on the canonical
`p0` shape, post-N5a/N5b. Scope is intentionally narrow:

- `p0` only at budgets 8 and 32. `p1`/EOG is excluded from Phase 1
  timing — Phase 0 already pinned its semantics, and timing an
  EOG-stop shape (hpx `n_decoded=0`, llama `tokens_predicted=1`) is
  not informative.
- Non-streaming and streaming runs, in that order.
- 51 iterations per `(server, workload)`. Exp12's `bench.py`
  records iterations as 1-indexed (`iteration == 1..51`). **The
  first measured iteration (`iteration == 1`) is treated as warm-up**
  for timing aggregates; reported percentiles are computed over
  `iteration ∈ [2, 51]` (n=50). Correctness, anchor, and per-server
  stability gates are evaluated over all 51 rows.

Configs:

- `config.phase1.nonstreaming.json` — 2 workloads × 51 iters.
- `config.phase1.streaming.json` — 2 workloads × 51 iters,
  `streaming: true`.

Run commands (from the Exp12 directory, re-rooting results under
Exp15):

```text
cd hpx-bench/experiments/12_hpx_vs_llama_server_pair

python3 bench.py \
  --config       ../15_hpx_vs_llama_server_semantics/config.phase1.nonstreaming.json \
  --results-root ../15_hpx_vs_llama_server_semantics/results

python3 bench.py \
  --config       ../15_hpx_vs_llama_server_semantics/config.phase1.streaming.json \
  --results-root ../15_hpx_vs_llama_server_semantics/results
```

Driver `stdout` / `stderr` capture under
`local/runs/exp15/phase1-{nonstreaming,streaming}/` (gitignored).
Each `bench.py` invocation produces a `results/<run-id>-pair/`
subtree with the same shape as Phase 0.

Comparable metrics (client-side monotonic, include loopback;
field names are exactly as Exp12's `client_results.jsonl` writes
them):

- non-streaming: `latency_ms` p50 / p95 / p99.
- streaming: `first_event_latency_ms`, `first_token_latency_ms`,
  `total_latency_ms` percentiles; inter-event gaps derived per row
  from `token_event_times_ms` (consecutive differences) then
  flattened across iterations; optional derived tokens/sec from
  `n_decoded * 1000 / total_latency_ms`, caveated.

Record-only fields carry forward from Phase 0:
`text`/`text_sha256`/`text_normalized_sha256` cross-server equality,
hpx-server's missing `prompt_tokens` vs llama-server's
`tokens_evaluated`, streaming detokenization divergence, llama-server's
missing `hash` field. None of these is timed or gated cross-server.

## Non-claims

Phase 0 does not and cannot make any of these claims:

- No performance claim. No throughput, latency, TTFT, or
  responsiveness comparison between the two servers.
- No concurrent-client claim. Single client only.
- No cross-server text-equality gate. BOS, leading-space, and
  sampler-chain asymmetries documented in
  `known_mismatches.txt` make byte equality not meaningful.
- No cross-server streaming token-event-count equality.
- No production-server claim. Single machine (Apple M4 Pro, darwin),
  single model (TinyLlama Q4_K_M).

Phase 1 additionally does not:

- Claim a "winner" or use comparative wording (`faster`, `slower`,
  `wins`, `beats`, `outperforms`, `better`, `worse`, `speedup`,
  `regression`). Values are reported descriptively (e.g. "observed
  p50 is lower/higher", "recorded latency differs by …").
- Generalize beyond `p0`, budgets 8/32, single-client greedy on this
  hardware/model.
- Treat `p1`/EOG timings as Phase 1 evidence (excluded by construction).

## Phase 2a-S0 — concurrent harness smoke

Phase 2 will compare the two servers under multiple simultaneous
client requests, preserving every Phase 0 semantic caveat. Before
running the full Phase 2a queue-pressure matrix, **Phase 2a-S0** runs
a tiny smoke against a new concurrent driver to validate the harness,
schema, process lifecycle, and gates. S0 is **not** a performance
slice; it is a harness-correctness slice.

### New driver

`hpx-bench/experiments/15_hpx_vs_llama_server_semantics/concurrent_bench.py`

- Python 3 stdlib only.
- **Reuses Exp12 unchanged**: imports `adapters.hpx_server` and
  `adapters.llama_server` for request bodies / response parsing, and
  imports the helpers `tcp_wait`, `http_post_json`, `launch_server`,
  `stop_server`, `write_args_file`, `server_pid_running` from Exp12's
  `bench` module. Exp12 source is read-only.
- One server boots at a time. Each server is launched **once per
  run** and all concurrency cells share that boot, which sidesteps
  port reuse / TIME_WAIT by construction. hpx-server first, then
  llama-server.
- Concurrent clients are threads synchronized on a
  `threading.Barrier` at the start of each `(server, concurrency)`
  cell; within a client, iterations run back-to-back with no
  inter-iteration delay.

### S0 scope

- Non-streaming only.
- Workload: `p0_b8` (canonical anchor) only.
- Concurrency levels: `[1, 2]`.
- Iterations per client: `6` (drop `iteration == 1` per client as
  warm-up; correctness gates use all rows).
- One config: `config.phase2a.smoke.p0_b8.json`.

### S0 run command

```text
cd hpx-bench/experiments/15_hpx_vs_llama_server_semantics

python3 concurrent_bench.py \
  --config       config.phase2a.smoke.p0_b8.json \
  --results-root results
```

Capture driver `stdout` / `stderr` under
`local/runs/exp15/phase2a-smoke-p0_b8-nonstreaming/` (gitignored).
Each invocation produces `results/<YYYYMMDD-HHMMSS>-c-smoke/` with
`config.json`, `client_results.jsonl`, `summary.csv`, `run_notes.txt`,
and per-server `stdout` / `stderr` / `args`.

### S0 gates (all must pass)

- Every row: `http_status == 200`, `parse_error == ""`,
  `failed_reason == ""`, `n_decoded == 8`.
- Every hpx-server row: `hash == 0x0619d4d1900c2365`.
- Per `(server, concurrency)`: `text_normalized_sha256` stable
  across the cell's rows.
- No stuck `llama-server` or `llama-hpx-server` process after either
  cell.
- `run_notes.txt` free of forbidden comparative words.

### S0 non-claims

- Not a timing slice. Latencies are recorded but **not** interpreted,
  not aggregated as percentiles, and not compared between servers.
- Not a concurrency-capacity claim. `c ∈ {1, 2}` only.
- All Phase 0 / Phase 1 non-claims still apply (no winner language,
  no semantic equality, no production claim, no generalization
  beyond this machine/model/prompt/budget).

S0 must pass before the full Phase 2a queue-pressure matrix
(`c ∈ {1, 2, 4, 8}`, 51 iterations per client, `p0_b8` then
`p0_b32`, streaming deferred) is authorized.

### S0 outcome (run 20260524-221428-c-smoke)

S0 was run once and **failed the original "every row HTTP 200"
gate**. The failure is recorded as a real semantic finding, not a
harness defect; see `results.md` "Experiment 15 — Phase 2a-S0
results" for the full per-cell numbers and the failing-row detail.

Headline finding: under matched single-slot admission
(`hpx --max-concurrent 1`, `llama --parallel 1`), the two servers'
externally observable overload responses differ.

- **hpx-server**: rejects fast with **HTTP 503** when the
  externally-issued client count exceeds `--max-concurrent`. In the
  S0 `c=2` cell, hpx-server admitted client_id=0's six requests
  (HTTP 200, canonical hash held) and rejected all six of
  client_id=1's requests with HTTP 503.
- **llama-server**: queues the excess client and serializes
  admission. In the matching `c=2` cell, both clients' requests
  completed and the cell's wall-clock approximately doubled,
  consistent with sequential admission on the single slot.

This is an **admission-policy** difference, not a bug in either
server. Phase 0 and Phase 1 were single-client and could not have
exercised it.

## Phase 2 — future work (post-S0 reshape)

Phase 2 is split into two tracks. Each track has its own settings,
gates, and reported descriptors; see `facts.md`
"Phase 2 gate policy" for the formal gate definitions.

- **Phase 2a — admission / rejection semantics under overload.**
  Keeps the matched `--max-concurrent 1` / `--parallel 1` settings
  and treats HTTP 503 from hpx-server as a **recorded, allowed**
  outcome when the client count exceeds the admission slot count.
  Reports `completed_count`, `rejected_count`, `rejected_rate`, and
  HTTP-200-row stability gates. Latency aggregates are **not**
  computed cross-server in 2a because the successful-request
  populations differ.

- **Phase 2b — admitted parallelism with matched N.**
  Configures both servers for matched in-flight admission
  (`hpx-server --n-seq-max N --max-concurrent N` vs
  `llama-server --parallel N`, first cut `N ∈ {2, 4}`). All rows are
  expected to return HTTP 200. This is the correct track for any
  latency-under-load side-by-side. Phase 2b runs only after Phase 2a
  is recorded and a matched-N smoke (2b-S0) is passed.

**Retry-on-503 is intentionally not enabled in the harness.**
Enabling it would mask the admission-policy divergence that
Phase 2a is designed to record. If a future slice wants to measure
end-to-end latency with retry, it will be defined as an explicit,
separately scoped experiment with its own gates.

## Phase 2b-S0 — admitted-parallelism smoke

Phase 2b-S0 validates the admitted-parallelism track of Phase 2:
both servers are configured to admit `N = 2` in-flight requests, two
concurrent clients submit through the same `concurrent_bench.py`
harness, and every row is required to return HTTP 200.

### Harness change for Phase 2b

`concurrent_bench.py` gains an optional config block:

```jsonc
"server_args": {
  "hpx_server":   { "n_seq_max": N, "max_concurrent": N,
                    "max_prompt_tokens": 512 },
  "llama_server": { "parallel": N, "no_context_shift": true,
                    "seed": 0 }
}
```

When present, the harness builds argv from this block (per-server
builders inside `concurrent_bench.py`). When absent, it falls back
to `adapter.build_args(cfg, port)` so the existing Phase 2a-S0
config runs **byte-identically**. Exp12 adapters are still imported
for request bodies and response parsing; no semantic parsing logic
is duplicated.

### Phase 2b-S0 scope

- Non-streaming only.
- Workload `p0_b8` only.
- Concurrency levels `[1, 2]`.
- Iterations per client `6` (warm-up drops `iteration == 1`).
- hpx-server: `--n-seq-max 2 --max-concurrent 2`.
- llama-server: `--parallel 2`.
- Config: `config.phase2b.smoke.p0_b8.json`.

### Phase 2b-S0 run command

```text
cd hpx-bench/experiments/15_hpx_vs_llama_server_semantics

python3 concurrent_bench.py \
  --config       config.phase2b.smoke.p0_b8.json \
  --results-root results
```

Driver capture under
`local/runs/exp15/phase2b-smoke-p0_b8-nonstreaming/` (gitignored).

### Phase 2b-S0 gate policy (strict)

- Every row: `http_status == 200`, `parse_error == ""`,
  `failed_reason == ""`, `n_decoded == 8`.
- Every hpx-server row: `hash == 0x0619d4d1900c2365` (the Phase 1
  canonical anchor).
- Per `(server, concurrency)`: `text_normalized_sha256` stable
  across the cell.
- No `503` from either server (this is the distinguishing gate vs
  Phase 2a).
- No timeouts; no stuck processes; `run_notes.txt` free of
  forbidden comparative wording.

The canonical hpx-server hash at `c = 2` is **not assumed** in
advance — Phase 1 measured it at `--n-seq-max 1`. Three outcomes
are anticipated and handled explicitly in the gate logic:

- Case A: every hpx `c=2` row matches `0x0619d4d1900c2365` → PASS.
- Case B: every hpx `c=2` row has a single, stable, non-canonical
  hash → controlled finding, not an automatic failure. Record the
  new hash as a candidate N=2 anchor; do not declare PASS; do not
  canonicalize without approval.
- Case C: hpx `c=2` hash varies across rows → correctness concern;
  stop and report.

### S0 outcome (run 20260524-222733-c-smoke) — Case A, PASS

Both servers admitted both concurrent clients cleanly. Every row
returned HTTP 200; the hpx-server canonical anchor
`0x0619d4d1900c2365` held at both `c=1` and `c=2`; per-server
`text_normalized_sha256` is stable across every cell; no stuck
processes; forbidden-word audit clean. Per-cell numbers and
descriptive timing are recorded in `results.md`.

Phase 2b-S0 does not authorize the full Phase 2b matrix (`N ∈
{2, 4}`, `c ∈ {1, 2, 4, 8}`, 51 iterations per client, `p0_b8` and
`p0_b32`, streaming deferred). The matrix is a separate design
slice with its own scope, run plan, and gates.
